# Live text trace — 0.1.0

PPSSPP v1.20.4 was copied into the ignored `work/source/ppsspp` folder with its own memory stick, settings and save data. Original-ISO experiments used the interpreter/software renderer; the later local menu-test ISO was cold-booted in the same isolated setup. The local debugger listens on loopback port 45373. No user emulator settings or existing saves were changed.

`tools/ppsspp_debug.py` uses the documented debugger WebSocket protocol. `tools/capture_frame.py` probes the game's display-buffer import, reads software-rendered emulated VRAM, removes its breakpoint and resumes execution. It prints parameters by default; `--write` saves a native 480 × 272 PNG and metadata. This fallback does not claim to capture hardware-renderer framebuffers.

The actual module load base is **0x08804000**. At module offset `0x29414c`, the imported `sceDisplaySetFrameBuf` stub selects buffers with a 512-pixel stride. The title/menu use RGBA5551 at alternating `0x04000000` / `0x04044000`; the opening movie was observed using RGBA8888 at `0x04088000`. Captures are under `work/ui/runtime`. File offsets below map to module offsets by subtracting `0xc0` in the first load segment.

The five main-menu labels reside inside the executable code section's embedded string pool, starting at file `0x94f43`. This pool was omitted by the initial non-code-section string scanner. The labels were observed on the main menu and queued separately; other labels in the same pool still require audit. The initial 640 heuristic candidates must not be treated as exhaustive.

A read breakpoint on the first menu label at runtime `0x08898e83` reached the CP932 decoder at module `0xe9c64`, including its second-byte read at `0xe9c94`. The decoder stores a character word through a2 and a 1- or 2-byte input length through a1. Its return flag is 1 for CP932 double-byte characters and 0 for single-byte characters. Callers observed in the trace were `0xead20` (control/count helper, return at `0xeade8`) and the drawing loop (return at `0x87d38`).

In the original drawing loop, module `0x87d54` prepares a double-byte glyph draw. It calls `0xe9918` or `0xea45c`, supplying a nominal 16 × 16 glyph rectangle. At `0x87dc4`, the cursor adds f26 to f22. The live main-menu state had f22=11, f24=147, f26=13, f28=16. This establishes **13px fixed horizontal advance on this menu path**, not every game text path. The adjacent routine at `0x880c8` has related count/centering behavior and needs review too.

Original single-byte printable characters follow the control-handling branch on this drawing path. A VWF needs ASCII classification as well as glyph lookup, drawing, advance widths and measurement/centering. The resident map contains fullwidth Latin CP932 codes, rather than plain ASCII. The experiment therefore adds Latin records and rasterized glyphs, preserving original records and pixels.

The resident glyph routine at `0xea45c` receives a font-state pointer in a0. For nominal size 16, characters below `0x889f` use the descriptor at state+4, other characters use state+8; size 8 uses state+12. Each descriptor contains count, table pointer, and pixel pointer. The table has 12-byte records: u32 character code, float slot index, float third value (observed -1). Slot indices select 384-byte packed alpha4 glyphs, 32x24 pixels, low nibble first. It uploads a glyph through `0x1b7e1c` and draws a nominal 16x16 rectangle through `0xd7fc`. The resource-specific routine `0xe9918` uses another bank and remains outside the English demo.

On this load, font state was `0x09e72d40`; first bank descriptor `0x08c80bd0` held 230 glyphs, table `0x08cb5950`, pixels `0x09dfb440`. These heap/runtime pointers are observations, not permanent file offsets. The installer obtains state through `0xe928c` each time. Five menu string references are at module `0x948d4`, and their original string addresses are `0x94e83`, `0x94e90`, `0x94e97`, `0x94ea2`, `0x94ead` plus the module base.

The tested payload uses newly allocated game memory. The decoder-return trampoline at `0xe9cc8` changes classification only when ra is `base+0x87d38`; the cursor trampoline at `0x87dc0` uses float advances for Latin and f26 for original Japanese glyphs. f26 stays intact. All five labels were observed at x=11, y=147/167/187/207/227 with proportional cursor differences of 4–12px. New Game totals 69px advance; Data Install totals 74px. See the native screenshot and 76-draw trace under `work/ui/runtime`.

The original Japanese options screen remained readable during the test. All font/menu/code changes were then verified, restored and the owned allocation freed; the original ISO and decrypted ELF were never edited. This evidence establishes a reversible native menu VWF, not full dialogue support or a persistent build.

The later 4x-source test adds upload/mode/draw wrappers at `0xea5c4`, `0xea6a0` and `0xea6e4`. Original delay instructions at the latter two calls remain untouched. The owned payload is 221,840 bytes in a 233,472-byte block. A code-to-slot lookup covers 22 high-resolution glyphs; unavailable glyphs and Japanese records follow the native route. Packed 4-bit 128×64 uploads use independent 64×64 source/16×16 destination extents through `0xd8e4`. The 76-draw trace confirms these dimensions and the same five label positions/advances. The frame was visually checked at native 480×272; it does not establish increased emulator rendering resolution. Filtering remains inherited and unmeasured.

The 4x test also preserved the Japanese Options screen. Rollback validated all seven change ranges and the payload hash, restored them, waited two display frames and freed the block. `main_menu_restored_after_4x.png` visibly confirms the Japanese menu after free. The full 96-glyph high-resolution block failed allocation before any hook was installed, motivating a subset test and future memory-efficient coverage.

The persistent menu candidate now cold-boots with its six hook sites, five menu pointers and resident descriptor validated in actual loaded memory. The new static segment increases module size to 24,313,344 bytes. A separate 76-draw trace verifies the same five labels and 4x source extents without runtime patch installation. Japanese Options and protagonist selection remain readable. See `MENU_BUILD.md` and `cold_boot_menu_validation.en.json` for the limited evidence.

Next: inspect `0xe9918` and every measurement/cursor caller; verify ruby/control behavior; relocate a dialogue sample; test wrapping, centering and clipping. Expand 4x coverage within measured memory limits and test increased emulator rendering resolution. See `font_format.md`, `VWF.md` and `prx_relocation.md`.

## Resource fonts and dialogue layout: static follow-up

A later actual opening-scene trace identifies **font mode 1 → E9FF4**, not E9918, for the first Keroro speech bubble. The body pointer maps uniquely to `fld/talk/f101010.bin` offset 3912 (reference 1). Sixty-four draws confirm 16×16 rectangles, 13px advances, line origins (310,168)/(310,190), and a 45-glyph reveal setting. The scene remained Japanese in the 0.1.0 menu candidate. `trace_dialogue.py`, `opening_dialogue_trace.en.json` and `DIALOGUE_BUILD.md` record the evidence and separate relocated assets. Extending E9918 alone would miss this observed opening path.

The 0.1.1 compact 4x menu candidate also cold-boots. All 96 high-resolution slots and lookup entries match loaded memory; a separate 76-draw trace verifies the five menu labels with 64×64 upload/pitch and 64×64 source/16×16 destination rectangles. Japanese Options remains readable. This bank expansion adds no dialogue hooks or translated story data.

Read-only disassembly of the original decrypted ELF establishes the `0xe9918` ABI: A0 font manager, A1 integer x, A2 integer y, A3 destination width, T0 destination height, T1 low-16 character code, T2 resource-bank index. A3=8 bypasses this routine's upload; other widths select the resource bank. Getter `0x84114` supplies its array base; bank stride is `0x3830`, charset starts at bank+`0x10`, packed pixels at +`0x60`, and a lookup-table pointer resides at +`0x37e0`. Binary search uses 12-byte records and compares the first u16; the float at +4 selects a 384-byte pixel slot. Upload at `0xe9a64` uses 32×24/pitch32 T4 pixels; drawing at `0xe9ac0` uses the same context and destination arguments as the resident renderer. This is a resource object layout, distinct from the resident manager's count/table/pixels descriptor.

Direct calls to E9918 are `0x517c0`, `0x87d8c`, `0x8823c`, `0xebeac`, and `0xee330`. An entry wrapper can test T1, preserve arguments and RA, then **tail-jump to EA45C only for supported English codes and the intended nominal-size paths**. Japanese must execute the original resource renderer. This is statically feasible, not yet implemented or tested. Width13 at `0x517c0`, width8 bypass, palette/effect state, and scaled text need separate handling. The existing high-resolution source hook already preserves EA45C destination extents, but its compact atlas covers only the menu repertoire.

The shared decoder E9C64 returns consumed bytes through A1's pointer, u16 code through A2's pointer, and V0=1 for CP932 double-byte glyphs. It is also used by numeric/control argument scanners. **Do not classify printable ASCII globally:** the subordinate scanner at EAE9C, for example, uses the result while skipping control arguments. Gate visible-text scanners by audited return PC and preserve argument/skip scans. Existing menu gate `0x87d38` covers only one draw loop; another at `0x881e8` needs its own classification/advance handling and routes its ordinary-font glyphs to EAB10 rather than EA45C.

Important layout sites, all module-relative:

| Routine/site | Verified behavior | VWF implication |
| --- | --- | --- |
| `0x87c18` generic draw | Optional origin adjustment at `87cc4` multiplies glyph count from EAD20 by caller advance; glyph cursor adds F26 at `87dc4`; control `0x11` resets x and adds F28 to y at `880bc–880c4` | Replace pixel measurement and retain control semantics; count×advance is not an English width measure |
| `0x880c8` second generic draw | Same count/origin adjustment at `88174`; fixed cursor advance at `88274` | Separate hook coverage required |
| `0xead20` visible glyph counter | Top-level decoder returns at EADE8; visible glyph increments FP at EAE08; final return EB83C supplies integer count | English glyph counting/reveal capacity must be addressed without changing subordinate control scans; do not change this integer API to pixels globally |
| `0xe9cd0` delimiter counter | Counts requested low-byte delimiter A1 and handles other control cases | Line/page counts, not a pixel-width function |
| `0xe9e28` line scanner | Returns a pointer after an interpreted delimiter/control boundary | Preserve boundaries while relocating text |
| `0xebc08`, caller `0xde1b4` | Special layout path: resource scan EBE24 draws E9918 and increments integer x offset by 13 at EBEB8; normal branch scans EBFF0, draws E9FF4 and advances by 13 at EC054; position/effect vector also advances F26 by F28=13 | Requires coordinated position and visible-count updates, not only renderer redirection |
| `0xee968` object construction | Sets text/current pointers at object+0/+4; default glyph count 45 at +0xc; control-aware preparatory scan at `0xeeaac` | Long English lines may exceed existing count/capacity assumptions |
| `0xee448` progression | Scans text at EE670, compares visible count and handles control results via EED34; preserves/restores current pointer | Audit reveal timing and control interpretation before widening ASCII classification |
| `0xee208` renderer dispatch | Resource branch EE330→E9918; other branches include EA45C, E9FF4, EA718 | Dialogue can enter several rendering modes |
| `0xeeba8–0xeec0c` subordinate span scan | Counts glyphs until `0x0f`, then computes 13×count/2 for a position adjustment | Ruby/span positioning is fixed-width; numeric count is not sufficient for VWF |

No automatic word-wrap routine was verified in this pass. The observed paths consume existing control-delimited lines, fixed glyph limits and explicit pixel/count arithmetic; identifying a count does not establish wrapping. The next safe extension is a relocated, control-light dialogue sample with targeted decoder gates, English-only E9918 redirection, matching advance/measurement, and count/reveal checks. Ruby spans, alternate fonts, clipping, scaled glyphs and complete dialogue coverage remain unverified. No emulator connection or binary modification was used for this follow-up.
